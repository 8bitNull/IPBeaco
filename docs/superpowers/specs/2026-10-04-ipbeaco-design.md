# IPBeaco 第一版设计

日期：2026-10-04\
状态：用户已确认，进入实现计划阶段；尚未开始实现。订阅文件统一放入 `lists/` 目录。

## 1. 目标与范围

在 GitHub 维护可追溯、定期更新、可订阅的 IP 情报。第一版包含三个独立用途：

1. Web 入站防护：封禁、观察两档，IPv4/IPv6 分开。
2. 网络防护：独立的 IPv4/IPv6 CIDR 网段列表。
3. 出站防护：独立的 IPv4/IPv6 僵尸网络 C2 地址列表。

默认工作流使用公开、无需密钥且再分发依据明确的来源。AbuseIPDB 作为可选补充设计，默认关闭。不同用途不合并为一个总封禁列表；同一地址可在不同用途出现，但 Web 封禁档与观察档互斥。

第一版不包含管理后台、在线查询 API、数据库服务、主动扫描、自动修改用户防火墙规则、ASN 路由封禁或厂商专用推送。项目代码开源与上游数据许可分别管理，不能用项目代码许可证覆盖上游数据。

## 2. 技术与调度

- Python 负责采集、清洗、规则判断、状态保存和导出。
- GitHub Actions 每天 UTC 00:17（北京时间 08:17）调度，支持手动触发。定时执行可能延迟，不承诺准点。
- 主分支保存代码、来源配置、规则、文档和测试；独立 `data` 分支保存持久状态。
- GitHub Pages 发布静态订阅文件及状态说明。运行时不依赖独立服务器。
- 所有更新和部署任务使用同一并发组，串行执行；不在中途取消正在保存状态或部署的任务。
- Actions 缓存仅用于加速，不能作为唯一状态存储。

## 3. 来源准入与候选清单

每个来源必须登记：官方地址、下载地址、数据类型、网络方向、许可依据及核查日期、署名要求、来源家族、时间语义、更新周期、允许的最高档位、解析器和响应大小限制。必须分别通过授权、语义、格式、新鲜度检查才能启用。

| 来源 | 实际核查 | 第一版处理 |

候选来源数不等于有效独立证据数。来源下载成功也不等于授权、语义或时效合格。发布前可以继续增加独立的 Web 来源，但每个新增来源都必须满足同一准入门槛。

### 3.2 上线边界

首版实现应支持以上三类输出，但不能保证候选来源都能立即提供合格数据。技术验收与有效情报上线分开：某类没有合格来源时，标记 `unavailable`，不得声称该类已具备实际防护覆盖。取得授权、修复上游分类问题或等到新鲜数据出现是启用条件，不通过降低规则绕过。

## 4. 数据模型与模块

五个模块通过结构化记录交互，不直接相互修改内部状态：

1. 来源适配器：下载、限制响应体大小、解析并输出来源快照。
2. 数据清洗：IP/CIDR 标准化、公网校验、去重及白名单过滤。
3. 策略判断：来源独立性、时间有效性、用途、分档及过期处理。
4. 状态存储：跨运行保存证据、过期记录、来源状态和运行清单。
5. 文件发布：稳定排序、生成文件、校验、生成 Pages 部署产物。

证据记录至少包含：对象（IP 或 CIDR）、地址族、用途、攻击分类、来源 ID、来源家族、首次获取时间、本次获取时间、上游观测时间（可为空）、快照生成时间（可为空）、证据时间依据、失效时间、允许档位和原因代码。

时间统一使用 UTC。必须区分本地下载时间、上游文件生成时间和攻击观测时间。上游不提供的字段保持空值，不能伪造。对明显位于未来的上游时间（超过当前时间 5 分钟）拒绝作为有效证据。

来源状态包含：是否启用、最近尝试/成功时间、上游时间、文件摘要、解析计数、失败原因和准入状态。日志不得输出密钥。

## 5. 三类列表的规则

### 5.1 Web 封禁与观察

封禁条件：经人工审核为高可信且允许进入封禁档的来源提供近期 Web 攻击证据，或至少两个已验证独立来源家族提供近期相关证据。普通扫描或信誉分高不能自动等同于 Web 攻击。具体来源资格由配置明确声明，不能让解析器自行升级。

- 有单条攻击观测时间：封禁证据最长有效 72 小时；观察证据最长有效 7 天，自观测时间计算。
- 封禁证据失效后，只能依据仍有效的观察证据降档；没有证据则移除。
- 多来源判定每次重新检查每条证据是否有效，不能只取最新时间保留已经不满足条件的封禁。
- 同一上游被转载多次只算一个家族；独立性不能确认时，不计入多源封禁条件。
- Web 两档互斥，不跨用途去重掉网段或 C2 记录。

对于具有明确滚动窗口的来源，可以在单独审核后采用快照证据。例如经确认真实反映最近 48 小时攻击的快照，最多再有效 24 小时，以保证最旧攻击不超过 72 小时。计算起点必须是可信的上游快照时间，不能是本地下载时间；相同快照不会续期。该例不代表 blocklist.de 已通过此项审核。

对于没有可靠观测时间、窗口或生成时间的来源，最多进入观察档，从首次发现起保留 7 天。保留过期标记，持续出现在同一来源不自动续期。只有后续完整、成功且有效的快照确认消失，再出现时才开始新的观察周期；采集失败不算消失。与 Web 用途无关的通用数据不进入这两档。

### 5.2 网段列表

- 接受上游明确发布的公网 CIDR，分 IPv4/IPv6 输出，保留原始网段边界与来源。
- 不把单 IP 自动聚合成更大的网段，不展开 CIDR 成海量 IP，不接收 ASN-DROP。
- 采用完整快照替换语义：上游有效新快照删除的网段，在下一次发布中删除。
- 每个来源快照最长有效 48 小时，自可信上游生成时间计算；重复下载旧快照不续期。
- 若合法的上游有效期更短，采用较短者。无法确定快照时间的来源不默认启用。
- 网段与白名单有任何地址重叠时，首版保守移除整个网段并记录原因，避免白名单中的单 IP 仍被覆盖；不实现复杂的网段切割。

### 5.3 出站 C2 列表

- 只接收明确指向 botnet C2 目的地址的数据，不把这些地址作为 Web 攻击来源证据。
- Feodo 优先采用官方当前推荐的有效列表，不采用 aggressive 历史合集。
- 使用有效完整快照替换，来源移除或证据到期即删除。
- 快照最长有效 48 小时，若有更短的上游有效期则从其规定；不把文件生成时间解释为逐条在线检测时间。
- HTTP 成功但快照陈旧为 `stale`；新鲜、可验证且为空的快照为 `empty`，两者不混淆。

### 5.4 通用清洗与白名单

使用标准 IP 解析，不用字符串正则作为最终有效性依据。过滤私网、回环、链路本地、多播、未指定和保留用途地址；CIDR 必须整体符合公网策略。公网判断规则与依赖版本在测试中固定。

项目白名单影响公共产物。Fork 用户可配置自己的白名单；直接订阅公共文件的用户在本地执行自己的排除规则，公共列表无法替所有使用者应用私有白名单。

## 6. 发布契约

固定订阅路径（相对于 GitHub Pages 项目根地址）：

| 路径 | 内容 |
| --- | --- |
| `lists/block-ipv4.txt` / `lists/block-ipv6.txt` | Web 封禁，逐行 IP，无注释 |
| `lists/observe-ipv4.txt` / `lists/observe-ipv6.txt` | Web 观察，逐行 IP，无注释 |
| `lists/network-ipv4.txt` / `lists/network-ipv6.txt` | 独立 CIDR 网段，保留来源要求的日期、署名和版权头 |
| `lists/c2-ipv4.txt` / `lists/c2-ipv6.txt` | 出站 C2 目的地址，逐行 IP；仅接入允许此格式发布的来源 |
| `lists/status.json` | 构建版本、时间、各来源与各列表状态、数量、摘要和有效期 |
| `lists/metadata.json` | 可公开的来源、每条记录证据时间、收录/排除原因和许可关联 |

例如 `https://<用户名>.github.io/IPBeaco/lists/block-ipv4.txt`。WAF 调取具体文件 URL；是否支持自动订阅、CIDR 或注释由设备能力决定。原始来源先经筛选和去重，再进入对应用途文件，使用者不必逐个订阅上游。

网段文件的注释语法和署名格式以获准来源格式为依据，在接入文档明确设备兼容性。不能满足版权保留要求的无注释变体不提供；不把署名只放在 README 当作当然满足数据文件要求。

同一版本的文件、状态和元数据从同一份冻结状态生成并作为一个 Pages 产物部署。TXT 消费者的多次 HTTP 请求仍可能跨越部署或 CDN 缓存版本；严格一致的客户端应读取 `status.json`，验证文件摘要，发生变化则重试。

列表状态至少包含 `ok`、`empty`、`degraded`、`stale`、`unavailable`。`status.json` 为每类产物提供独立的有效截止时间，以保守覆盖其中最早将到期的证据。全局构建时间不能替代某一来源的新鲜度。

尚无合格数据的列表在初始发布中可以为空，但状态必须为 `unavailable`，接入文档禁止将这种空文件解释为可健康同步的清空指令。有效来源确认没有符合条件的记录才标记 `empty`。

## 7. 状态、异常与发布事务

每次运行读取上一份状态，采集、清洗、计算过期，生成候选状态和产物，全部校验通过后提交 `data` 分支，再部署对应产物。状态提交失败时不部署；部署失败时保留已提交候选状态和运行版本，以便重试。

重试部署之前必须重新检查证据有效期，不能在数日后原样发布已经过期的旧产物。公开状态中的版本号代表实际部署版本，不假设 `data` 最新提交已上线。

- 单个来源失败：继续处理其他来源，失败来源的历史证据只保留到原失效时间，发布状态为降级。
- 所有来源请求失败但历史状态可读取：仍可完成过期计算并发布降级状态；此时空结果不能标记为健康的 `empty`。
- 运行整体失败或状态损坏：不覆盖上一份部署；GitHub Actions 报错。禁止把损坏状态当作首次运行，从而重置证据寿命。
- 数量异常：对非首次有效快照，新增条目达到 1,000 且总量超过上一有效快照的 3 倍时触发审查；阈值可配置。发生异常的快照不替换旧证据，其他来源与到期清理继续处理。
- 正常到期删除不触发“数量下降即拒绝发布”；合法空快照通过来源结构和时间检查后可接受。
- 解析失败、HTML 冒充列表、超限响应和无效时间均拒绝该快照，不从错误页中随意提取 IP。

这将此前“数量异常就暂停整个发布”的初步设想细化为隔离异常来源，避免无关记录的过期清理也被暂停。

静态 Pages 文件无法在 Actions 完全停运时自行过期。接入方必须检查 `status.json` 的有效期，并对本地规则设置失效策略；只会下载 TXT 的设备需要外部同步脚本或人工监控，项目不能承诺这类设备自动撤销陈旧规则。

`data` 分支只保存允许公开的结构化状态，不提交原始下载全集或凭据。保留所有仍有效证据与用于阻止旧证据续期的标记，运行明细保留最近 30 天。Git 历史仍会增长，README 明确说明；首版不自动重写远端历史。

## 8. 测试与验收

自动测试采用固定样本和可控时钟，不依赖实时网站可用性。必须覆盖：

1. IPv4/IPv6/CIDR 清洗、特殊地址过滤、白名单及 CIDR 重叠。
2. 重复下载不续期、未来时间拒绝、滚动窗口边界、到期降档和删除。
3. 转载不能凑足独立来源、两档互斥、不同用途不混入。
4. 无时间来源的过期标记和消失后重新出现流程。
5. 陈旧快照、合法空快照、来源失败、异常增长和格式改变。
6. 全部来源失败时仍计算到期；首次无可用来源标记 `unavailable`。
7. 状态提交失败、部署失败重试、损坏状态拒绝、串行运行。
8. 稳定排序、摘要匹配、跨文件版本一致、署名与版权信息保留。

上线前对每个拟启用来源执行一次真实只读验证，核实格式、时间、语义和授权记录。测试通过不意味着上游已获得授权或数据足够新鲜。尚无合格来源的用途只验收其功能支持，不宣称实际覆盖上线。

## 9. 文档与交付

README 提供项目定位、三类用途、八个订阅地址、更新频率、当前来源状态、首次部署与 Fork 说明、WAF/防火墙容量及格式限制、陈旧数据处理和误报反馈入口。

来源说明单独记录许可及核查结果；所有失败显示在 Actions 日志与能够成功发布的状态页中。第一版不自动给他人发送邮件或消息。

本设计批准后，下一步编写实现计划。GitHub 远端仓库创建和实际发布需要在执行阶段确定所属账号与仓库地址；本设计不假设远端仓库已经存在。
